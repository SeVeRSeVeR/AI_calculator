# ASSUMPTIONS

Документ фиксирует все допущения калькулятора, коэффициенты формул и известные расхождения с иллюстративными примерами исходного технического задания. Версия формул: **calc v1.0**. Версия каталога: **2026.11**, дата сбора: **2026-11-16**.

Принцип: если в ТЗ или источнике нет однозначного значения, выбирается консервативный вариант, а место помечается в коде комментарием `// ASSUMPTION:`.

## 1. Единицы и округления

- Все объёмы памяти внутри расчёта — в **ГБ** (десятичных, `1e9` байт), а не в ГиБ. Это соответствует тому, как производители обычно указывают VRAM и как считает ТЗ.
- Пропускная способность — в **ГБ/с** (десятичных).
- Токены и параметры — в штуках; параметры моделей — в миллиардах (`params_total_b`, `params_active_b`).
- Промежуточные значения не округляются. Округление выполняется только для отображения: `round(value, 2)`.
- `effectiveContext = min(requested, model.max_context)`, но не меньше 1. UI дополнительно валидирует превышение максимума модели.
- Вместимость KV-пула (`maxParallel`) округляется **вниз** до целого числа последовательностей.
- RAM, БП и NVMe округляются **вверх** до стандартных номиналов: RAM `8/16/32/64/128/256/512`, БП `650/850/1000/1200/1600/2000`, NVMe `1/2/4/8/16/32 ТБ`.

## 2. Веса модели

```
weights_gb = params_total_b × bytes_per_param × 1.05
```

- **1.05** — 5% на эмбеддинги, нормы, выходной слой, метаданные и неучтённые служебные тензоры. Для квантованных чекпойнтов часть тензоров часто остаётся в FP16, поэтому запас нужен.
- Для MoE **всегда используется `params_total_b`**, даже если активных параметров в разы меньше. Все веса должны находиться в памяти (или быть выгружены), активность влияет только на скорость.
- `bytes_per_param` — из каталога квантизаций. Значения для 4-битных форматов (`0.55`) включают служебные шкалы/группы и упаковку, а не идеальные `0.5`.
- GGUF-значения (`1.06`, `0.82`, `0.70`, `0.55`, `0.43`) — эффективные байты на параметр с учётом метаданных и квантованных тензоров, а не точная битность.
- Формула не учитывает LoRA-адаптеры, мультимодальные проекторы и отдельные vision-энкодеры. Для моделей с такими компонентами запас 5% может быть недостаточен.

## 3. KV-кеш

```
kv_per_token_gb = 2 × n_layers × n_kv_heads × head_dim × kv_bytes_per_elem / 1e9
kv_required_gb  = kv_per_token_gb × context_tokens × users
```

- **2** — ключи и значения.
- `n_layers`, `n_kv_heads`, `head_dim` берутся из каталога, то есть из `config.json` модели, и **не выводятся** из `hidden_size / n_heads`. Это важно для Gemma (head_dim 256), MLA-моделей DeepSeek/Kimi (head_dim 576) и GQA/MQA.
- Для MLA-моделей (`deepseek-v3`, `deepseek-v4-flash`, `deepseek-v4-pro`, `kimi-k2.6`) в каталоге указаны эффективные `n_kv_heads = 1` и `head_dim = 576`, что даёт сжатый KV-кеш, близкий к публичным оценкам. Точная формула MLA включает latent-вектор и rope-часть; упрощение выбрано консервативно и одинаково для всех MLA-моделей.
- `kv_bytes_per_elem` берётся из квантизации: FP16/BF16 и большинство GGUF — 2 байта, FP8/INT8 — 1 байт. Для 4-битных GPU-квантизаций KV обычно остаётся в FP16, поэтому указано 2 байта.
- KV-кеш не выгружается в RAM в текущей версии. Параметр `kvOffloadedGb` в платформенной рекомендации зарезервирован, но равен 0.
- Не учитываются prefix caching, paged attention, сжатие KV и разделение KV между пользователями. Это делает оценку консервативной для движков с prefix caching.

## 4. Резерв VRAM и workspace

```
overhead_gb  = 1.5 × gpu_count + engine.overhead_gb
workspace_gb = 0.05 × allocated_vram_gb
allocated_vram_gb = physical_vram_gb × util_target
```

- **1.5 ГБ на каждую GPU** — CUDA context, драйверные аллокации, фрагментация. В ТЗ упоминалось 0.6 ГБ, но для реальных CUDA-контекстов и нескольких процессов этого мало; выбрано консервативное значение. Именно оно приводит к расхождению с тестом 2 (см. §13).
- `engine.overhead_gb = 1.5` для всех движков — CUDA graphs, activations, profiling reservation, служебные буферы. Для llama.cpp фактический compute buffer зависит от `n_batch` и `n_ubatch`; 1.5 ГБ — оценка.
- **5% workspace** — активации, временные буферы, фрагментация. Считается от уже урезанной (`util_target`) VRAM.
- NCCL-буфер: **0.5 ГБ** для PCIe, **0.75 ГБ** для NVLink/Infinity Fabric, только при `gpu_count > 1` и `engine.supports_tp = true`. Для llama.cpp layer-split NCCL не добавляется.
- `util_target` по умолчанию: vLLM/TGI/SGLang — **0.90**, llama.cpp — **0.95**. Пользователь может задать 0.80–0.95. Значение ограничивается диапазоном 0.5–1.0 внутри ядра.
- Для режима B OPTIMAL принудительно используется `util_target = 0.90`, чтобы конфигурации были сопоставимы независимо от движка.

## 5. Per-GPU fit

```
per_gpu_footprint = weights / gpu_count + kv_pool / gpu_count + 1.5 + nccl
fit_per_gpu       = per_gpu_footprint ≤ min(vram_gb всех GPU)
```

- Используется **минимальная** VRAM среди карт, а не сумма. Калькулятор предполагает одинаковые GPU, но формула защищает и от разнородной конфигурации.
- KV-пул делится поровну между картами. Это оптимистично для tensor parallel с дисбалансом, но консервативно по сравнению с проверкой только суммарной VRAM.
- Проверка per-GPU не заменяет проверку `kv_pool > 0`: обе должны выполняться.
- Если per-GPU footprint превышает VRAM, но суммарно память есть, статус — `NO_FIT` или offload, а не «помещается».

## 6. Offload

Offload разрешён только движкам с `offload_supported = true` (в каталоге — llama.cpp).

- Веса выгружаются **целыми слоями**: `layer_size = weights / n_layers`, число слоёв округляется вверх. Это отражает `n_gpu_layers` в llama.cpp и не даёт произвольную долю веса.
- `MAX_OFFLOAD_RATIO = 0.5` — жёсткий предел: больше половины весов в RAM считается неприемлемым.
- Для MIN-конфигурации дополнительно требуется `offload_ratio ≤ 0.4`.
- Скорость при offload: `penalty = 1 / (1 + 2.5 × offload_ratio)`, ограничено снизу 0.08. То есть 10% offload дают ~0.8×, 40% — ~0.5×. Коэффициент **2.5** — допущение: RAM и PCIe заметно медленнее VRAM, но не линейно в 10–20 раз.
- RAM для offload: `max(weights_offloaded + 6, 1.3 × weights_offloaded)`. 6 ГБ — ОС, драйверы и page cache; 1.3 — запас на фрагментацию и буферы.
- Offload-feasible требует одновременно: `offload_ratio ≤ 0.5`, per-GPU fit, `maxParallel ≥ users`, `kv_required > 0`, `vram_used ≤ physical_vram`.
- Не моделируется частичный offload KV-кеша, `--n-cpu-moe`, SSD-Offload и гибридный offload различных движков.

## 7. Скорость

Скорость decode считается memory-bandwidth-bound:

```
bw_effective = Σ bandwidth_gbs × tp_factor
tok_per_seq  = (bw_effective × 1e9 × speed_efficiency) / (params_active_b × bytes_per_param × 1e9) × offload_penalty
total_tok_s  = tok_per_seq × maxParallel × batch_efficiency
```

- Используется `params_active_b`: для dense это равно total, для MoE — активные параметры. Это ключевое отличие MoE от dense.
- `tp_factor`: 1 GPU — 1.0; unified memory — 1.0; NVLink/Infinity Fabric — 0.65; PCIe TP — 0.35; llama.cpp layer-split — 0.85. Потери на all-reduce и синхронизацию.
- `speed_efficiency`: 1 GPU или unified — 0.55; layer-split — 0.55; NVLink/Infinity Fabric TP — 0.65; PCIe TP — 0.40.
- `batch_efficiency`: `≤8` последовательностей — 0.85; `≤32` — 0.60; больше — 0.45. Профиль нагрузки умножает значение: chat 1.0, RAG 0.95, code 0.90, batch 1.05; результат ограничен 0.30–1.0.
- `tokPerSeqMin/Max` — ±30% как грубый коридор неопределённости. Итоговый дисклеймер говорит о ±15% для всей конфигурации; эти числа не противоречат друг другу: ±30% относится к скорости, ±15% — к сводной оценке памяти/платформы.
- Не моделируются prefill, TTFT, speculative decoding, flash attention, кэш промпта, NUMA и thermal throttling. Оценка относится к decode-фазе.
- Профили нагрузки задают целевой tok/s: chat 15, RAG 25, code 20, batch 40. Значения выбраны как типичные пользовательские пороги, а не как бенчмарки.

## 8. Платформа: CPU, RAM, NVMe, БП, охлаждение

- Требуемые линии PCIe: `(datacenter ? 8 : 16) × gpu_count`; для unified memory — 0. 8 линий на датацентровую карту — допущение о типичном riser/backplane, а не о физическом максимуме.
- Минимум ядер CPU: `max(8, 2 × gpu_count)`, плюс 4 ядра при offload.
- RAM без offload — минимум 16 ГБ, округлённый до модуля. С запасом на ОС и page cache.
- NVMe: `max(1024, weights_gb × 5 × 1.2)` — хранение пяти копий модели (разные кванты, чекпойнты) с запасом 20%.
- БП: `ceil((Σ TDP GPU + TDP CPU + 150) × 1.3)`, затем округление до стандартного номинала. 150 Вт — материнская плата, диски, вентиляторы; 1.3 — запас на пики.
- Охлаждение: до 600 Вт GPU — воздушное; 600–1200 Вт — СЖО 360 мм или серверные турбины; ≥1200 Вт — СЖО/жидкостное. Порог — допущение.
- Цена: `price_usd` GPU × количество + цена выбранного CPU. **RAM, NVMe, материнская плата, корпус, БП и охлаждение в цену не входят.** Это оценка «от GPU и CPU», а не полная смета. Если цена GPU отсутствует, конфигурация считается бесконечно дорогой при сортировке.
- Для unified memory отдельная планка RAM не суммируется с VRAM; выводится предупреждение. CALC не моделирует разделение пула между CPU и GPU.
- SXM/OAM-карты требуют серверного шасси с высоконапорными вентиляторами. Калькулятор предупреждает, но не подбирает шасси, backplane и riser.

## 9. Режим A

- Проверяются все модели со статусом `released`.
- Статусы:
  - `FITS_FULL` — per-GPU fit, `kv_pool > 0`, запас `kv_pool / allocated_vram ≥ 0.15`;
  - `FITS_TIGHT` — per-GPU fit и `kv_pool > 0`, но запас < 15%;
  - `FITS_WITH_RAM` — полное размещение не проходит, но offload feasible;
  - `NO_FIT` — не проходит ни один вариант.
- Сортировка: сначала по статусу (`FULL → TIGHT → RAM → NO_FIT`), внутри статуса — по убыванию `params_total_b`.
- `servesRequestedUsers` — отдельный флаг: `maxParallel ≥ users`. Он **не меняет** статус fit, потому что статус описывает размещение модели, а не обслуживание всех пользователей. UI показывает предупреждение, если пользователей больше, чем помещается в KV-пул.
- Если задан `targetToks` в расширенных параметрах, он используется для пометки/фильтрации в UI; базовый fit от него не зависит.
- Рекомендация платформы в режиме A показывается для выбранной модели. Если модель не выбрана — платформа не показывается, чтобы не создавать ложное впечатление точной сметы.

## 10. Режим B: MIN, OPTIMAL, MAX

Движок выбирается автоматически по семейству квантизации:

- `gguf` → **llama.cpp**;
- `gpu` → **vLLM**.

Это зафиксированное допущение: пользователь режима B задаёт модель и квантизацию, но не движок. TGI и SGLang доступны в режиме A; в режиме B они не выбираются, чтобы не умножать число неоднозначных сценариев.

### MIN

- Полное размещение в VRAM либо offload не более 40%.
- `maxParallel ≥ users`.
- `tok_per_seq ≥ 0.5 × targetToks` — минимальная конфигурация может быть медленнее целевой, но не в разы.
- Сортировка: меньшая физическая VRAM → меньший offload → меньшая цена → меньше GPU.
- MIN — самая дешёвая/маленькая конфигурация, которая ещё обслуживает нагрузку, а не «конфигурация с запасом».

### OPTIMAL

- `util_target = 0.90`.
- `maxParallel ≥ users`.
- Запас VRAM `spare_ratio ≥ 0.15`.
- `tok_per_seq ≥ targetToks`.
- Физическая VRAM не меньше, чем у MIN.
- Предпочтение: сначала конфигурации с запасом ≤ 0.30, затем дешёвые, затем с меньшей VRAM, затем с большим запасом. Если конфигураций с запасом 15–30% нет, выбирается вариант с запасом > 30%.

### MAX

- Физическая VRAM не меньше OPTIMAL.
- `spare_ratio ≥ 0.40`.
- `maxParallel ≥ max(2 × users, 2 × maxParallel OPTIMAL)`.
- `tok_per_seq ≥ targetToks`.
- Приоритет — минимальная VRAM, покрывающая **1.5× VRAM OPTIMAL**, затем цена.
- Если 1.5× недостижимо, берётся максимальная доступная конфигурация с предупреждением.
- Если строгие критерии MAX не выполняются, берётся крупнейшая совместимая конфигурация с предупреждением.
- Если MAX совпадает с OPTIMAL по модели GPU и количеству, `max` обнуляется, а `maxEqualsOptimal = true`. UI показывает явное сообщение, а не дублирующую карточку.

### Инвариант `min ≤ optimal ≤ max`

- Проверяется по физической VRAM, RAM, ядрам CPU и мощности БП.
- Offload-MIN может требовать больше RAM, CPU и БП, чем OPTIMAL без offload. Чтобы инвариант выполнялся, RAM/PSU OPTIMAL и MAX **выравниваются вверх** до значений MIN, а ядра CPU при необходимости повышаются.
- Это намеренное завышение платформы, а не ошибка: конфигурация, позиционируемая как «лучше MIN», не должна требовать меньше ресурсов, чем MIN.
- Если `max` отсутствует, инвариант проверяется только для `min ≤ optimal`.

### IMPOSSIBLE

Возвращается, если не удалось найти OPTIMAL. Причина: модель не помещается полностью в VRAM при заданных пользователях, контексте и квантизации. Рекомендации формируются в порядке:

1. уменьшить контекст вдвое (не ниже 512);
2. снизить квантизацию в том же семействе;
3. взять меньшую released-модель, которая помещается на 8 самых больших не-unified GPU с тем же контекстом и пользователями.

Рекомендации — эвристика, а не гарантированный рецепт. Они не учитывают смену движка, кроме автоматического выбора по семейству квантизации.

## 11. Unified memory и специальные платформы

- `dgx_spark` и `mac_studio_m3_ultra` помечены `unified_memory = true`.
- Для них `interconnect = unified`, `tp_factor = 1`, `speed_efficiency = 0.55`, отдельная планка RAM не добавляется.
- Комбинации с несколькими unified-устройствами не рассматриваются: `listCombos` для unified создаёт только `count = 1`.
- Это упрощение: реальный unified-пул имеет свою пропускную способность и ограничения по выделению, а CPU и GPU конкурируют за память.
- ROCm-совместимость отмечена флагом `rocm_support`, но отдельные поправки к скорости для ROCm не применяются. Это консервативно: реальная скорость может отличаться.

## 12. Данные, цены и версионирование

- Каталог статичен. Версия `2026.11` и дата `2026-11-16` означают срез на эту дату, а не автоматическое обновление.
- Цены — ориентировочные розничные/уличные в USD на дату сбора. Они быстро меняются, не включают налоги, доставку и региональные наценки.

- Характеристики моделей — из `config.json` на Hugging Face; для будущих/неопубликованных на дату сбора моделей использованы публичные анонсы и консервативные оценки. Такие записи помечены в `DATA_SOURCES.md`.
- `catalog_version` и `collected_at` дублируются в каждом файле каталога. Загрузчик берёт версию из models/gpus, но schema требует согласованности.
- Runtime-валидация каталога в браузере облегчена (проверяются ключевые поля), полная валидация JSON-схемами выполняется в CI через AJV.

- `localStorage` хранит `llmcalc.v1`. При несовместимом изменении формы нужно поднять ключ или добавить миграцию; сейчас неизвестные/невалидные поля отбрасываются при чтении.

## 13. Расхождения с иллюстративными ожиданиями ТЗ

Формулы реализованы строго по §4 ТЗ. В трёх местах иллюстративные ожидания примеров не совпали с результатом строгих формул. Тесты фиксируют фактическое поведение, а не подгоняются под пример.

### Тест 2: 2×RTX 4090, 70B Q4_K_M, 8K, 2 пользователя

- Ожидание примера: `FITS_TIGHT`.
- Фактически: `FITS_WITH_RAM`, offload около 12%.
- Причина: 70B Q4 даёт ~40.8 ГБ весов с запасом 5%; в 2×24 ГБ после `util_target`, 1.5 ГБ CUDA-контекста на карту, 5% workspace и KV-кеша остаётся недостаточно для полного размещения. Модель помещается с небольшим offload.
- Тест проверяет `FITS_WITH_RAM`, `0 < offload_ratio ≤ 0.5`, per-GPU footprint ≤ 24 ГБ и предупреждение PCIe.
- Если бы использовалось 0.6 ГБ CUDA-контекста из ранней версии ТЗ, результат был бы ближе к `FITS_TIGHT`; выбрано консервативное 1.5 ГБ.

### Тест 3: 4×A100 80GB, 70B FP16, 32K, 50 пользователей

- Ожидание примера: конфигурация обслуживает 50 пользователей.
- Фактически: `status = FITS_FULL`, но `maxParallel < 50`, `servesRequestedUsers = false`.
- Причина: KV-кеш 50 × 32K × FP16 для 70B физически не помещается в 320 ГБ вместе с весами. Статус fit описывает размещение модели, а не обслуживание всех пользователей; для этого есть отдельный флаг и предупреждение.
- Рабочий вариант в тесте: FP8, 8K, 50 пользователей — `maxParallel ≥ 50`, `servesRequestedUsers = true`.
- Это осознанное разделение статуса и флага, а не ошибка расчёта.

### Тест 8: случай `optimal == max`

- В исходном примере для 8B Q4 4K 1 пользователя ожидались три различимые конфигурации. На практике для маленькой модели на минимальном железе MIN и OPTIMAL могут совпасть, а MAX может упереться в потолок каталога или критерий 1.5×.
- Реализованный тест 8 проверяет коллапс на гигантской MoE: `deepseek-v4-pro`, Q4_K_M, 4K, 1000 пользователей, профиль batch. Здесь `optimal` существует, `max` отсутствует, `maxEqualsOptimal = true`.
- Тест 6 отдельно проверяет, что для 8B Q4 4K **5 пользователей** три конфигурации различимы.
- Причина возможного коллапса: критерии MAX (1.5× VRAM, запас ≥40%, параллелизм ×2) могут быть недостижимы в каталоге; тогда MAX не дублирует OPTIMAL, а помечается как «каталог исчерпан».
- В ТЗ не был задан приоритет между «всегда показать MAX» и «не дублировать OPTIMAL». Выбран второй вариант как более честный для пользователя.

## 14. Прочие допущения и ограничения

- Модели с `status != 'released'` не участвуют в расчётах. В текущем каталоге все 32 модели `released`.
- Каталог не учитывает лицензии моделей и ограничения коммерческого использования. Перед продакшеном проверяйте лицензию.
- Не моделируются: NVMe-Offload, SSD-Offload, CPU-инференс без GPU, тензорный параллелизм с разнородными картами, MIG, vGPU, спот-инстансы и облачные цены.
- Не моделируются: ECC, коррекция ошибок, резервирование VRAM под монитор, несколько процессов на одной GPU.
- Предупреждение о PCIe TP появляется для мульти-GPU без NVLink/Infinity Fabric. Для llama.cpp layer-split предупреждение тоже показывается, хотя штраф там меньше; рекомендация предлагает layer-split как предпочтительный вариант.
- Кнопка «Снизить квантизацию» в пустом состоянии режима A ищет более низкую квантизацию в текущем семействе. Если её нет, переключает на GGUF `Q3_K_M` и llama.cpp. Это зафиксированное поведение (см. `// ASSUMPTION:` в `src/state/store.ts`).
- Share-link содержит только параметры формы, не результаты. При открытии ссылки результаты пересчитываются из текущего каталога, поэтому могут отличаться после обновления данных.
- Неизвестные query-параметры игнорируются, пользователь получает уведомление. Невалидные значения также игнорируются и заменяются значениями по умолчанию или сохранённым состоянием.
- `localStorage` может быть недоступен (приватный режим, политики браузера); ошибки записи молча игнорируются, приложение продолжает работать.
- Копирование ссылки использует Clipboard API с fallback на `execCommand('copy')`; при полном запрете буфера обмена показывается сообщение об ошибке.
- Сборка не содержит source maps и внешней аналитики.
- Зависимости разработки могут содержать уязвимости, о которых сообщает `npm audit`. Они не попадают в статический бандл; перед публикацией рекомендуется регулярно проверять и обновлять lockfile.
